# Comments on Tasks — Feature Design Plan

**Proposed documentation path:** `docs/decisions/comments-feature-plan.md`  
**Status:** Planning only; no implementation approved.

## Context

The Task Tracker currently stores tasks through Pydantic models in `app/models.py`, FastAPI routes in `app/main.py`, and JSON persistence in `app/storage.py`. The frontend is a single HTML file containing its HTML, CSS, and JavaScript at `frontend/index.html`.

This plan follows the Module 5 guardrails in `AGENTS.md:321-381`: inspect first, keep the task bounded, and do not modify `app/` without explicit approval.

---

## 1. Data Model

### Model location

The comment models should be added to `app/models.py`.

This matches the existing repository structure:

- `TaskCreate` is defined at `app/models.py:32-45`.
- `TaskUpdate` is defined at `app/models.py:48-64`.
- `TaskResponse` is defined at `app/models.py:67-78`.
- All existing request and response models use `ConfigDict(extra="forbid")`.

A minimal first version should add two comment models:

### `CommentCreate`

Client-supplied fields:

| Field | Type | Validation |
|---|---|---|
| `author` | String | Required; 1–100 characters |
| `body` | String | Required; 1–2000 characters |

The model should forbid unknown fields, matching the existing task models.

The client should not be allowed to provide:

- `id`
- `task_id`
- `created_at`

Those values should come from the route and storage layer.

### `CommentResponse`

Returned and persisted fields:

| Field | Type | Source |
|---|---|---|
| `id` | String UUID | Generated by the backend |
| `task_id` | String | Taken from the task route |
| `author` | String | Validated client input |
| `body` | String | Validated client input |
| `created_at` | UTC datetime | Generated by the backend |

The response model should also forbid unknown fields.

### Validation approach

The repository currently uses a shared validator function to trim and validate task titles at `app/models.py:20-29`. Comment validation should follow the same general pattern rather than introducing a different validation style without a reason.

The implementation should decide whether:

- Leading and trailing whitespace are removed from `author`.
- Leading and trailing whitespace are removed from `body`.
- Whitespace-only values count as empty.

The requirement says both values must contain at least one character, but whitespace behavior is not confirmed.

### Models not included in the initial scope

A `CommentUpdate` model is not required unless the team decides that comments can be edited.

The initial task response should not automatically include a full comments array. Existing task responses have a fixed task shape in `app/models.py:67-78`, and the existing task-list endpoint returns complete task objects from `app/main.py:83-117`.

Keeping comments behind separate endpoints avoids increasing every task-list response and avoids changing existing task data.

### Identifier and timestamp conventions

Comment creation should follow the existing task conventions in `app/storage.py:66-78`:

- Generate IDs with UUID4 and store them as strings.
- Generate `created_at` with a timezone-aware UTC datetime.
- Generate both values on the server.

No new dependency appears necessary. UUID and UTC datetime support already come from Python’s standard library, while FastAPI and Pydantic are already present in `requirements.txt:1-5`.

## 2. API Routes

All current routes are defined directly in `app/main.py:31-185`. No separate route modules or `APIRouter` structure are visible.

For the smallest repository-consistent change, comment routes should initially be added to `app/main.py`. Moving existing routes into new router files would be a separate refactoring task and is outside this feature plan.

### Recommended initial routes

#### Create a comment

| Property | Design |
|---|---|
| Method | `POST` |
| Path | `/tasks/{task_id}/comments` |
| Request body | `author` and `body` |
| Success status | HTTP 201 |
| Response body | Full `CommentResponse` |
| Parent check | The task must already exist |

Processing order:

1. FastAPI and Pydantic validate the request body.
2. The route checks whether `task_id` exists using the repository’s existing task lookup behavior.
3. The storage layer generates the comment UUID and UTC timestamp.
4. The comment is persisted.
5. The complete comment is returned.

Error cases:

- HTTP 404 when the task does not exist.
- HTTP 422 when `author` is missing, blank according to the selected whitespace policy, or longer than 100 characters.
- HTTP 422 when `body` is missing, blank according to the selected whitespace policy, or longer than 2000 characters.
- HTTP 422 when the request contains unknown fields such as client-supplied `id` or `created_at`.

The existing task routes use HTTP 404 with a readable `detail` message when a task is missing at `app/main.py:140-142` and `169-177`. The comment route should follow that convention.

#### List comments for a task

| Property | Design |
|---|---|
| Method | `GET` |
| Path | `/tasks/{task_id}/comments` |
| Request body | None |
| Success status | HTTP 200 |
| Response body | List of `CommentResponse` objects |
| Default ordering | Oldest first, subject to team confirmation |

Error and empty-state behavior:

- Return HTTP 404 when the parent task does not exist.
- Return HTTP 200 with an empty list when the task exists but has no comments.

Checking the parent task distinguishes “this task has no comments” from “this task does not exist.”

### Routes not included without an explicit decision

The following routes should not be implemented automatically because the requested feature does not state whether comments can be retrieved individually, edited, or deleted:

- `GET /tasks/{task_id}/comments/{comment_id}`
- `PATCH /tasks/{task_id}/comments/{comment_id}`
- `DELETE /tasks/{task_id}/comments/{comment_id}`

These operations belong in Open Questions.

### Route ownership checks

For any future route containing both `task_id` and `comment_id`, the backend must verify that the comment belongs to the task in the URL.

A comment must not be returned, updated, or deleted merely because its comment ID exists under a different task.

### Authentication limitation

The repository currently has no authentication or user identity model visible in `app/main.py`. Therefore, `author` would initially be client-supplied text rather than a verified signed-in user.

This is a course-scope limitation, not proof that an authentication feature is required for this bounded task.

## 3. Tests

### Test location and style

A focused new test file, `tests/test_comments.py`, would keep comment behavior separate from the existing task tests.

The preferred style should follow `tests/test_tasks.py`, which:

- Uses the shared `client` fixture.
- Creates prerequisite tasks through API calls.
- Checks response status and JSON fields.
- Uses descriptive names such as `test_create_task_valid_returns_201_with_full_body`.

The fixtures are defined in `tests/conftest.py:8-25`.

### Test-data isolation requirement

The current autouse fixture calls `storage._reset()` before and after each test at `tests/conftest.py:8-12`. That reset clears the normal task JSON file through `app/storage.py:219-223`.

Before comment tests are executed, the test design should be updated so both task and comment storage use isolated temporary data files. Comment tests should not add a second reset operation that clears another normal application data file.

### Happy-path tests

Recommended concrete test names:

- `test_create_comment_valid_returns_201_with_full_body`
  - Create a task.
  - Create a comment for it.
  - Verify `author`, `body`, and `task_id`.
  - Verify generated `id` and `created_at` are present.

- `test_create_comment_generates_uuid_string`
  - Verify the returned ID can be interpreted as a UUID and is serialized as a string.

- `test_create_comment_generates_utc_created_at`
  - Verify the timestamp is timezone-aware and represents UTC.

- `test_list_comments_for_task_returns_created_comments`
  - Create two comments for the same task.
  - Verify both are returned.

- `test_list_comments_for_task_with_no_comments_returns_empty_list`
  - Create a task without comments.
  - Verify HTTP 200 and an empty list.

- `test_list_comments_returns_comments_in_documented_order`
  - Create multiple comments.
  - Verify the chosen oldest-first or newest-first rule.

- `test_comments_persist_after_storage_reload`
  - Follow the persistence-testing idea used by `test_tasks_persist_after_module_reload` in `tests/test_api.py:101-110`.
  - Verify a stored comment remains available after the storage module reloads.

### Validation tests

Recommended concrete test names:

- `test_create_comment_missing_author_returns_422`
- `test_create_comment_blank_author_returns_422`
- `test_create_comment_author_at_100_characters_returns_201`
- `test_create_comment_author_over_100_characters_returns_422`
- `test_create_comment_missing_body_returns_422`
- `test_create_comment_blank_body_returns_422`
- `test_create_comment_body_at_2000_characters_returns_201`
- `test_create_comment_body_over_2000_characters_returns_422`
- `test_create_comment_unknown_field_returns_422`
- `test_create_comment_rejects_client_supplied_id`
- `test_create_comment_rejects_client_supplied_task_id`
- `test_create_comment_rejects_client_supplied_created_at`

The last three may be combined with the unknown-field test if all server-controlled fields are rejected by `extra="forbid"`.

### Edge-case tests

Recommended concrete test names:

- `test_create_comment_for_missing_task_returns_404`
- `test_list_comments_for_missing_task_returns_404`
- `test_list_comments_excludes_comments_from_other_tasks`
- `test_comment_task_id_matches_parent_route_task`
- `test_existing_tasks_remain_valid_when_comments_store_is_empty`
- `test_missing_comments_data_file_is_treated_as_empty`
- `test_task_deletion_applies_selected_comment_policy`

If individual comment routes are later approved:

- `test_get_comment_through_wrong_task_returns_404`
- `test_delete_comment_through_wrong_task_returns_404`
- `test_patch_comment_cannot_change_task_id`
- `test_patch_comment_cannot_change_created_at`

### Frontend tests

No JavaScript testing framework, package manager, or frontend-test command is visible. Automated frontend testing is therefore **not confirmed**.

For this repository, the implementation plan should include a manual browser checklist unless the team separately approves frontend test tooling.

## 4. Frontend Changes

### File affected

The visible frontend is entirely contained in:

- `frontend/index.html`

The same file currently contains:

- The Kanban board at `frontend/index.html:445-472`.
- The task create/edit modal at `frontend/index.html:475-580`.
- API configuration and application state beginning at `frontend/index.html:582-653`.
- Task submission logic at `frontend/index.html:793-867`.
- Task-card rendering at `frontend/index.html:869-1015`.
- Task retrieval at `frontend/index.html:1226-1280`.

No separate CSS or JavaScript files are visible.

### Recommended user interaction

Add a **Comments** button to each task card beside the existing Edit button.

The existing card action area is created at `frontend/index.html:997-1005`. Selecting Comments should open a separate comments modal for that task.

A separate modal is preferable to placing comments inside the existing task create/edit form because:

- The current modal is designed around creating and editing task fields.
- Comments require their own loading, empty, validation, and submission states.
- Opening comments should not risk submitting or changing task fields.
- The comments list may grow independently from the task form.

### Comments modal contents

The modal should display:

- The selected task’s title.
- A loading state while comments are fetched.
- An empty state when the task has no comments.
- A list of existing comments.
- Each comment’s author.
- Each comment’s body.
- Each comment’s creation time.
- An author input.
- A body textarea.
- An Add Comment button.
- A visible validation or API error area.

### Client-side validation

Before sending the request, the frontend should check:

- Author is present.
- Author does not exceed 100 characters.
- Body is present.
- Body does not exceed 2000 characters.

The HTML inputs should also use appropriate `maxlength` attributes.

Backend validation remains authoritative. Client-side validation only improves the user experience.

### API calls

When the modal opens:

- Request `GET /tasks/{task_id}/comments`.
- Show loading, empty, ready, or error state.

When the form is submitted:

- Request `POST /tasks/{task_id}/comments`.
- Send only `author` and `body`.
- On success, clear the body field and refresh or append the new comment.
- On failure, display the backend’s readable error.

This should follow the existing request and error-handling pattern used by `submitTaskForm()` at `frontend/index.html:793-867`.

### Safe rendering

Comment authors and bodies are user-controlled text.

The frontend already defines `escapeText()` at `frontend/index.html:655-662` and uses it before inserting task data into `innerHTML` at `frontend/index.html:933-1005`.

Comment content must use the same escaping protection or be assigned through `textContent`. Raw author or body values must not be inserted directly into `innerHTML`.

### Comment counts

The initial version should not display comment counts on every card unless the API design is expanded.

The current `GET /tasks` response does not include comment information. Displaying counts would otherwise require either:

- One additional comments request per task, creating many browser requests, or
- Adding a `comment_count` field to task responses.

That decision should be made separately.

### Manual frontend verification

Because automated frontend tests are not configured, the manual checklist should verify:

- Comments modal opens for the correct task.
- Existing comments load.
- Empty state appears correctly.
- Valid comments can be submitted.
- Invalid lengths show useful errors.
- Server errors do not close the modal.
- Comment text containing HTML-like characters displays as text.
- Keyboard focus enters the modal.
- Escape and close controls behave consistently with the existing task modal.
- Comments from one task do not appear under another task.

## 5. Migration Notes

### Recommended persistence shape

The recommended initial design is a separate file:

- `data/comments.json`

The existing task file should remain:

- `data/tasks.json`

This preserves the current task shape and avoids modifying every existing task record.

The comments file should use the same broad storage convention as tasks: a JSON object keyed by generated comment ID, with each value matching `CommentResponse`.

Conceptual shape:

- Top-level key: comment UUID
- Stored record: `id`, `task_id`, `author`, `body`, and `created_at`

This is a task reference, not a database-enforced foreign key. The application must enforce that `task_id` refers to an existing task.

### Storage location

For minimum structural change, comment persistence functions can be added to `app/storage.py`, where task loading, saving, creation, lookup, and deletion already live.

Expected storage responsibilities include:

- Load comments from the comments data file.
- Save comments.
- Add a comment.
- List comments for a task.
- Optionally retrieve a comment by ID if later routes require it.
- Apply the selected task-deletion policy.
- Reset or isolate comment storage during tests.

A future split into `task_storage.py` and `comment_storage.py` would be a refactoring decision, not a requirement for the first implementation.

### Existing task data

Existing records in `data/tasks.json` need no transformation under the separate-file design.

Every existing task begins with zero comments until comments are created.

No new field needs to be inserted into `TaskResponse`, and existing clients can continue reading task responses without modification.

### Task deletion

The team must choose a deletion policy.

The recommended default is to delete a task’s comments when the task is deleted so that comments do not become orphaned.

That would require the existing task-deletion flow at `app/main.py:181-185` and `app/storage.py:195-216` to coordinate comment removal.

Alternative policies are listed under Open Questions.

### Loading and corrupt data

The existing task loader returns an empty task collection when its file is missing or contains invalid JSON at `app/storage.py:12-26`.

The comments implementation should explicitly decide whether to copy that behavior. Silently treating corrupted comments data as empty could hide data loss, so the preferred design is:

- Missing comments file: treat as an empty collection.
- Invalid comments JSON: report a visible storage error rather than silently replacing it.
- Invalid individual comment records: do not silently discard them without a documented recovery policy.

### Test-storage migration

The current tests use the normal storage reset mechanism, as documented in `AGENTS.md:138-155`.

Before adding comment tests, the project should establish isolated test paths for both:

- Task data
- Comment data

This avoids extending the existing risk of tests clearing normal local data.

## 6. Open Questions

### 1. Can comments be edited?

If yes, the design needs:

- A `CommentUpdate` model.
- A PATCH route.
- Rules for whether author, body, or both can change.
- A decision about whether the original `created_at` remains unchanged.
- Possibly an `updated_at` field, which is not part of the current comment requirement.

### 2. Can comments be deleted?

If yes, the team must decide:

- Whether deletion is permanent.
- Whether deleting a missing comment returns 404.
- Whether the comment must be addressed through its parent task route.
- Whether the UI includes delete controls.

### 3. What happens to comments when their task is deleted?

Options include:

- Delete comments automatically.
- Reject task deletion while comments exist.
- Keep orphaned comments.

Automatic deletion is recommended, but the team must confirm it.

### 4. How should whitespace be handled?

The requirements specify minimum lengths but do not state whether:

- `"   "` is a valid author.
- `"   "` is a valid body.
- Author values should be trimmed.
- Body formatting and leading spaces should be preserved.

This must be decided before validation tests are finalized.

### 5. In what order should comments appear?

Possible choices:

- Oldest first, like a conversation.
- Newest first, showing the latest activity immediately.

The API and frontend should use the same documented order.

### 6. Is the author free text or a verified user?

No authentication system is visible in the repository.

For the current course version, author can be free text. For any future authenticated version, the author should normally come from the signed-in identity rather than trusting a client-supplied name.

### 7. Should task responses include comment counts?

Adding `comment_count` could improve the Kanban interface, but it changes `TaskResponse` and the task-list storage/API behavior.

Without it, the frontend should avoid making one comments request for every task card.

### 8. Is pagination needed?

The initial course version may return all comments for one task.

A maximum comment count or pagination behavior is not visible in current requirements and remains **not confirmed**.
